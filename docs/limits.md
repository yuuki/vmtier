# Guarantees and limits

These constraints apply to both SQLite and PostgreSQL service backends unless a
backend-specific or legacy JSON v2 exception is stated. See [getting started](getting-started.md) for setup and
[operations](operations.md) for monitoring and recovery.


- Archive age H, allowed lateness L, and Hot retention R must satisfy `H > L >= 0` and `R > H + safety_margin + window`. Hot retention does not follow vmtier's watermark. vmtier does not automatically shorten retention or delete Hot data, and cannot prevent loss during an unbounded export or storage outage.
- Lateness is an external ingestion contract. A read gateway cannot block direct late writes, backfills, or deletes. Changes to archived windows and topology changes are unsupported. Block mutation APIs with upstream access controls.
- Guaranteed query coverage begins at `coverage_start_ms`. Earlier history is outside that guarantee. Queries requiring a gap in archived coverage fail instead of returning an incomplete successful result.
- Service deployments have one active archiver, fixed tenants, a pinned VM version, and **1 ms** deduplication. SQLite requires one owner; PostgreSQL permits multiple read gateways and automatically transfers archiver ownership using a fenced lease. The legacy JSON v2 runtime also requires one archiver. Unsupported RPCs, including Graphite, administration, writes, and deletes, return errors. Single-node VM integration is out of scope.
- Limits are 64 MiB per pack, 16 MiB per index, and 10,000 series and 100,000 blocks per pack. The service [rotates packs](archive-packs.md) within one immutable logical window; verified empty windows need no objects. Whole-window input, physical samples, pack count, and attempt time remain bounded. The retained JSON v2 writer stays single-pack and its catalog has a 10,000-entry lifetime limit; both service backends use bounded indexed selection without that lifetime cap. Run [preflight](preflight.md) before initialization because changing window width requires a new catalog.
- S3 needs ordinary PUT with Content-MD5, GET, and single-range GET, plus ordinary DeleteObject when [garbage collection](serve.md#garbage-collection) is enabled. Objects are read back and verified by length and SHA-256 before publication. Correctness does not depend on conditional PUT, ETags, or LIST. Storage classes requiring a restore operation before reads are unsupported. Moto and the compatibility proxy do not validate real-service authentication, durability, or performance.
- The catalog fixes coverage origin, window size, deduplication, H, L, tenants, and sources, and publishes with generation checks. Both service backends also fix the blob locator. SQLite holds a lifetime state-directory lock; PostgreSQL validates archiver fencing inside the publication transaction. Queries fail when the authority is unavailable. Offline SQLite backup/restore and JSON v2 import are implemented; restore requires a new catalog ID. Stopped-writer [SQLite-to-PostgreSQL migration](postgres-migration.md) preserves metadata and existing object references under a new identity. Recovery needs enough remaining Hot history to catch up. Backend migration does not upgrade a catalog or pack to a different VM pin. Automatic migration from the old all-S3 catalog is not available.
- SQLite S3 configurations default to 80 requests/s, eight in flight, and 64 queued requests through one shared budget. This covers a bucket only when this process is its sole client. Limits and actual Sakura performance require deployment testing; a dedicated prefix alone does not isolate provider quotas.
- PostgreSQL requires shared S3 and explicit aggregate S3 limits divided by `service.max_replicas`. Enforce that maximum across replicas, rollouts, and maintenance clients; static allocation does not fence additional S3 clients. Database HA, old-primary fencing, and a redundant Cold endpoint are operator responsibilities. See [HA deployment](ha-deployment.md) and [scoped fault evidence](postgres-ha-validation.md); acknowledged-commit durability depends on the database replication and promotion policy.
- Cold metadata still uses full validated block reads, with [bounded LRU caching and adjacent ranges](reader-validation.md). The earlier uncached S3 fixture exceeded vmselect's default five-second labels API deadline. The [before/after metadata measurements](metadata-validation.md) passed the retained fixture with the five-second deadline after the reader changes. The harness retains a configurable 30-second default; this does not establish an arbitrary-workload latency guarantee.
- Query admission reserves a per-query logical work allowance under a shared budget, including parsed-index estimates and copied result names. Cache flights, archive work, runtime overhead, and metadata serialization also consume memory; this is not a heap or RSS ceiling. See [component accounting](query-memory.md) and the [measured workload envelope](workload-validation.md), including the larger workload that exceeded the default query budget.
- Garbage collection deletes only the objects of failed attempts that the catalog recorded before upload; it is opt-in, and orphans from before the schema upgrade are not collected. Opt-in [Cold retention](serve.md#cold-retention) retires whole windows older than `cold_retention`; the range below a stream's retained start is outside the guarantee, and retired data is gone even if an older catalog backup is restored. Compaction (#45), downsampling (#46), and multipart upload (#47) remain unimplemented.
- VM frontend result caching is disabled in the MVP; the immutable Cold block cache is separate. Upstream public APIs do not expose immediate cancellation on client disconnect, so backend work can continue until its deadline.
